# 目的

このスキルは **Flutter アプリのアーキテクチャ決定フェーズ** を担当する。
`requirements.md` の内容を読み込み、プロジェクトの規模・要件に最適なアーキテクチャと
技術スタックをユーザーと合意し、`design.md` および `tech-stack.md` を更新する。

# このスキルを使うタイミング

以下の依頼を受けたときに起動すること:

- 「アーキテクチャを決めたい」「技術選定をしたい」
- 「状態管理・ルーティング・DI を何にするか決めたい」
- 「設計方針を整理したい」「設計書を作りたい」
- requirements-definition スキルの完了後に「次へ進む」と言われたとき

# 前提確認

スキル起動時にまず以下を確認する:

1. `.kiro/specs/` 配下に `requirements.md` が存在するか確認する
2. 存在する場合はその内容を読み込んでアーキテクチャ検討の入力とする
3. 存在しない場合は「要件定義が完了していません。先に requirements-definition スキルを実行してください」と案内する

# 進め方

## ステップ 1: 要件の読み取りと規模感の把握

`requirements.md` を読み込み、以下を推定してユーザーに提示する:

```
提示内容:
- アプリの規模感（小規模 / 中規模 / 大規模）の判断根拠
- 主要な技術的課題（例: リアルタイム同期が必要、複雑な状態管理が必要、など）
- 推奨アーキテクチャの候補（1〜2 案）
```

## ステップ 2: アーキテクチャ選定の対話

以下の観点を順番に確認・合意していく。1 メッセージに詰め込みすぎず、
トピックごとに **選択肢を提示 → ユーザーが選ぶ** 形式で進める。

### 確認項目と選択肢の例

```
① アーキテクチャパターン
   - Feature-First + Clean Architecture（推奨: 中〜大規模）
   - Feature-First + シンプル 3 層（推奨: 小〜中規模）
   - MVVM（推奨: 小規模・シンプル）

② 状態管理
   - Riverpod（推奨: 汎用性・テスタビリティ重視）
   - Bloc/Cubit（推奨: 複雑なビジネスロジック・大規模チーム）
   - Provider（推奨: 小規模・シンプル）
   - GetX（推奨: 素早いプロトタイプ）

③ ルーティング
   - go_router（推奨: Web 対応・ディープリンク必要）
   - auto_route（推奨: 型安全ルーティング重視）
   - Navigator 2.0 直接（推奨: シンプルなアプリ）

④ DI（依存性注入）
   - Riverpod（状態管理と統合）
   - get_it + injectable
   - なし（小規模）

⑤ ネットワーク層
   - Dio + Retrofit（推奨: REST API あり）
   - http パッケージ（推奨: シンプルな要件）
   - GraphQL Client（GraphQL の場合）

⑥ ローカルストレージ
   - Hive（推奨: 軽量・高速）
   - Isar（推奨: 複雑なクエリ必要）
   - SQLite / drift（推奨: リレーショナルデータ）
   - shared_preferences のみ（推奨: キー・バリューのみ）

⑦ コード生成ツール
   - freezed + json_serializable（推奨: 不変データクラス）
   - build_runner（推奨: 上記と組み合わせ）
```

## ステップ 3: ディレクトリ構成の確定

選定したアーキテクチャに基づき、具体的なディレクトリ構成案を提示して確認する。

## ステップ 4: 技術的リスクの共有

選定したスタックに伴う注意点・学習コスト・既知の制限を簡潔に伝える。

## ステップ 5: design.md の生成と tech-stack.md の更新

ユーザーの承認を得たら以下を実行する:
1. `.kiro/specs/<feature-name>/design.md` を生成する
2. `.kiro/steering/tech-stack.md` の「状態管理」「アーキテクチャ」「主要パッケージ」欄を更新する

# 生成ファイルのフォーマット

## design.md

```markdown
# 設計: <機能名・プロダクト名>

## アーキテクチャ概要

<選定したアーキテクチャの説明と選定理由>

## 技術スタック

| カテゴリ | 採用技術 | 選定理由 |
|---------|---------|---------|
| アーキテクチャ | <例: Feature-First + Clean Architecture> | <理由> |
| 状態管理 | <例: Riverpod> | <理由> |
| ルーティング | <例: go_router> | <理由> |
| ネットワーク | <例: Dio + Retrofit> | <理由> |
| ローカルDB | <例: Hive> | <理由> |
| コード生成 | <例: freezed, json_serializable> | <理由> |

## ディレクトリ構成

\`\`\`
lib/
├── main.dart
├── app.dart
├── core/
│   ├── constants/
│   ├── router/
│   └── theme/

        │   ├── datasources/
        │   ├── models/
        │   └── repositories/
        ├── domain/
        │   ├── entities/

        │   └── usecases/

            ├── widgets/

\`\`\`

## データフロー

<UI → Provider/Bloc → UseCase → Repository → DataSource の流れを説明>

## 主要な設計判断

### <判断事項 1>
- **決定**: <内容>
- **理由**: <理由>
- **却下した代替案**: <案と理由>

## 技術的リスク・注意点

- <リスク 1>: <対策>
- <リスク 2>: <対策>
```

# 対話のルール

- **必ず日本語で応答する**
- 選択肢は必ず **メリット・デメリット** を添えて提示する
- ユーザーが選択に迷っている場合は、**要件に基づいた推奨案を明示的に提示**する
- 技術選定の理由を必ず記録する（後から振り返れるように）
- 承認後は「次は設計・実装フェーズに進みますか？」と案内する
