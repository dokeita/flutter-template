# 目的

このスキルは **Flutter アプリの詳細設計・タスク分解・実装フェーズ** を担当する。
`requirements.md` と `design.md` を入力として、実装タスクを小さな単位に分解し、
ユーザーと進捗を確認しながら Flutter MCP を活用して実装・テスト・修正を行う。

# このスキルを使うタイミング

以下の依頼を受けたときに起動すること:

- 「設計・実装を始めたい」「コードを書いてほしい」
- 「タスクに分解したい」「何から始めればいいか整理したい」
- 「〇〇機能を実装してほしい」
- architecture-decision スキルの完了後に「次へ進む」と言われたとき

# 前提確認

スキル起動時にまず以下を確認する:

1. `.kiro/specs/` 配下に `requirements.md` と `design.md` が存在するか確認する
2. 存在する場合は両ファイルを読み込んで実装の方針とする
3. 存在しない場合は不足しているフェーズを案内する
   - `requirements.md` がない → requirements-definition スキルを先に実行
   - `design.md` がない → architecture-decision スキルを先に実行

# 進め方

## ステップ 1: タスク分解と tasks.md の生成

`requirements.md` と `design.md` を読み込み、実装タスクを以下の基準で分解する:

```
分解の基準:
- 1 タスク = 1 PR / 1 コミットに収まる粒度
- 依存関係を考慮して順序付けする
- フロントエンド・バックエンド（API連携等）を分離する
- テスト実装も別タスクとして立てる
```

**必ず T00 を最初のタスクとして追加する。**
T00 は steering ドキュメントと README.md をアプリ要件に合わせて更新するタスクで、
他のすべての実装タスクより先に実行する。

生成したタスクリストをユーザーに提示し、**順序・優先度・追加・削除の確認**を取る。

## ステップ 2: tasks.md の書き出し

ユーザー確認後、`.kiro/specs/<feature-name>/tasks.md` を生成する。

---

## tasks.md フォーマット

```markdown
# タスクリスト: <機能名>

## 進め方
各タスクを上から順に実装する。完了したら `[x]` にチェックを入れる。

## フェーズ 0: プロジェクト定義の更新

- [ ] **T00**: steering ドキュメントと README.md をアプリ要件に合わせて更新する
  - `.kiro/steering/product.md` をこのアプリのプロダクト概要・ターゲットユーザー・主要機能に書き換える
  - `.kiro/steering/tech-stack.md` の状態管理・アーキテクチャ・主要パッケージを design.md の決定内容に合わせて更新する
  - `README.md` のプロジェクト名・概要・セットアップ手順をこのアプリ向けに書き換える

## フェーズ 1: 基盤整備

- [ ] **T01**: プロジェクト初期セットアップ
  - flutter create でプロジェクト作成
  - analysis_options.yaml の設定
  - 依存パッケージの追加 (pubspec.yaml)
  - ディレクトリ構成の作成

- [ ] **T02**: コア層の実装
  - テーマ設定 (lib/core/theme/)
  - ルーター設定 (lib/core/router/)
  - 定数定義 (lib/core/constants/)

## フェーズ 2: <機能カテゴリ名>

- [ ] **T03**: <タスク名>
  - <サブタスク>
  - <サブタスク>

## フェーズ 3: テスト

- [ ] **T10**: ユニットテスト
  - Repository のテスト
  - UseCase のテスト
- [ ] **T11**: ウィジェットテスト
  - 主要 Widget のテスト
```

---

## ステップ 3: タスクの実装

ユーザーが「実装して」または特定のタスクを指定したら実装を開始する。
**Flutter MCP を積極的に使い**、実装・検証のループを回す。

### 実装サイクル（各タスクで繰り返す）

```
① コードを生成する
   └─ design.md のアーキテクチャ・命名規則に従う
   └─ flutter-best-practices.md の規約に従う

② Flutter MCP で検証する
   └─ analyze: 静的解析エラーを確認・修正
   └─ format: コードをフォーマット
   └─ test: テストを実行して確認（テストがある場合）

③ ランタイム確認（アプリ起動時）
   └─ get_runtime_errors: ランタイムエラーを確認
   └─ get_widget_tree: レイアウトを確認
   └─ hot_reload / hot_restart: 変更を反映

④ タスク完了の確認
   └─ tasks.md の該当タスクを [x] にチェック
   └─ 次のタスクをユーザーに確認して進む
```

### 実装時の必須ルール

- **1 タスク完了ごとに** `flutter analyze` と `flutter test` を実行する（MCP 経由）
- エラーが出たら **その場で修正**してから次のタスクへ進む
- コードを生成したら必ず `dart format` でフォーマットする（MCP 経由）
- 新しいパッケージが必要になったら `add_dependencies` ツールで追加する
- **途中で設計から外れる判断が必要な場合は実装を止め**、ユーザーに確認してから進む

## ステップ 4: 進捗の共有

各タスク完了時に以下を報告する:

```
✅ T03 完了: <タスク名>
   変更ファイル: <ファイルリスト>
   テスト: passed / failed（件数）
   次のタスク: T04 <タスク名> — 実装しますか？
```

## ステップ 5: 全タスク完了後の確認

全タスクが完了したら以下を実施する:

1. Flutter MCP の `test` ツールで全テストを実行する
2. Flutter MCP の `analyze` ツールで最終解析を行う
3. 結果をユーザーに報告する
4. `tasks.md` が全てチェック済みであることを確認する

# Flutter MCP ツールの使い方対応表

| やること | 使う MCP ツール |
|---------|----------------|
| 静的解析エラーの確認・修正 | `analyze` |
| コードフォーマット | `format` |
| テスト実行 | `test` |
| パッケージ追加 | `add_dependencies` |
| パッケージ検索 | `pub_dev_search` |
| アプリ起動 | `flutter_run` |
| ホットリロード | `hot_reload` |
| ランタイムエラー確認 | `get_runtime_errors` |
| Widget ツリー確認 | `get_widget_tree` |

# 対話のルール

- **必ず日本語で応答する**
- 実装前に「このタスクを実装します。よろしいですか？」と確認はしない（スムーズに進める）
- ただし **設計の変更・スコープの変更を伴う判断** が必要な場合は必ず確認する
- コードブロックには **必ずファイルパスを明示**する
- 長い実装は複数メッセージに分けず、**一気に実装してから MCP で検証**する
- エラーが解消できない場合は「詰まっている箇所と試したこと」をユーザーに共有する
