# 目的

このスキルは **Flutter アプリの要件定義フェーズ** を担当する。
ユーザーと対話しながら曖昧なアイデアを構造化された要件へと整理し、
後続のアーキテクチャ決定・設計・実装フェーズの入力となる `requirements.md` を生成する。

# このスキルを使うタイミング

以下のような依頼を受けたときに起動すること:

- 「要件定義をしたい」
- 「〇〇というアプリを作りたい」
- 「何を作るか整理したい」
- 「アプリの仕様・機能を決めたい」
- 「ユーザーストーリーを作りたい」
- Kiro の Spec モードで新しいスペックを開始したとき

# 進め方

## ステップ 1: アイデアのヒアリング（1 往復目）

ユーザーから **最初の 1 文** でアプリの概要を受け取ったら、以下を 1 メッセージにまとめて質問する。
一度に全部聞かず、**最大 3〜4 問** に絞ること。

```
質問すべき観点（優先度順）:
1. 誰のためのアプリか（ターゲットユーザー）
2. 解決したい課題・ペイン
3. 対応プラットフォーム（iOS / Android / Web など）
4. すでにイメージしている主要機能（あれば）
```

## ステップ 2: 深掘りヒアリング（必要に応じて 2〜3 往復）

回答を受けて不明点があれば追加質問する。以下の観点を漏れなく確認すること。

```
確認観点:
- 認証・ログインの要否
- オフライン動作の要否
- 外部サービス連携（API・SNS など）
- 非機能要件（パフォーマンス・セキュリティ・アクセシビリティ）
- スコープ外（明示的に作らないもの）
```

## ステップ 3: 要件の確認と合意

ヒアリング内容をもとに要件の **サマリーを箇条書きで提示** し、
「この認識で合っていますか？追加・修正はありますか？」と確認を取る。

## ステップ 4: requirements.md の生成

ユーザーの承認を得たら、以下の形式で `.kiro/specs/<feature-name>/requirements.md` を生成する。

---

# 生成ファイルのフォーマット

```markdown
# 要件定義: <機能名・プロダクト名>

## 概要

<アプリ・機能の 2〜3 行の説明>

## ターゲットユーザー

- <ユーザー像 1>
- <ユーザー像 2>

## 解決する課題

<ユーザーが抱える課題・ペイン>

## 機能要件

### <機能カテゴリ 1>

- WHEN <トリガー> THE SYSTEM SHALL <振る舞い>  ← EARS 記法
- WHEN <トリガー> THE SYSTEM SHALL <振る舞い>

### <機能カテゴリ 2>

- ...

## 非機能要件

- **パフォーマンス**: <例: 画面遷移は 300ms 以内>
- **セキュリティ**: <例: 認証トークンは安全に保存する>
- **対応プラットフォーム**: <iOS / Android / Web など>
- **アクセシビリティ**: <例: スクリーンリーダー対応>

## スコープ外（今回作らないもの）

- <スコープ外 1>
- <スコープ外 2>

## 受け入れ基準

- [ ] <テスト可能な条件 1>
- [ ] <テスト可能な条件 2>
```

---

# 対話のルール

- **必ず日本語で応答する**
- 一度に複数の質問をまとめる（会話の往復を最小化する）
- 技術的な詳細（実装方法・ライブラリ選定）はこのフェーズでは **扱わない**（次フェーズの話題）
- ユーザーが「わからない」と答えた項目は、一般的なベストプラクティスを提案して選んでもらう
- 要件は **EARS 記法**（`WHEN ... THE SYSTEM SHALL ...`）で記述し、曖昧さをなくす
- 生成後に「次はアーキテクチャ決定フェーズに進みますか？」と案内する
